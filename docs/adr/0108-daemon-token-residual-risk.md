# ADR-0108: daemon token運用における残留リスク

Status: Accepted
Date: 2026-09-15
Scope: daemon token fileの異常終了時の残留、復旧手順、および保護範囲
Related: [ADR-0107](0107-daemon-private-token-file.md)、[PR #391](https://github.com/zyx-corporation/chronicle-stack/pull/391)
Original draft: [PR #390](https://github.com/zyx-corporation/chronicle-stack/pull/390)

## 背景

CY-1の一環としてdaemon起動時のtoken運用を、`--session-token`のargv露出および起動時の
stdout／`--json`出力から、0600権限の専用ファイルへの生成方式に置き換えた。ファイルは
排他生成し、既存ファイル・symlinkを拒否する。daemon終了時には削除する。

本ADRは、利用者提供の「adr-daemon-token-residual-risk.md」を基に、異常終了時の残留リスクを
追加記録する。ADR-0107を補足し、現行の認証方式や既存ファイル拒否の決定を変更しない。

## 決定

token fileのライフサイクルをdaemonプロセス自身のクリーンアップ処理に委ねる。
生成は起動時の排他的なファイル作成、削除は正常終了・Ctrl-C・SIGTERM・起動失敗等で
クリーンアップが実行できる場合に行う。削除対象は生成したファイルと同じ識別情報を持つ
ファイルに限定し、別のファイルに置き換わっていた場合は削除しない。

SIGKILLや停電など、終了処理が実行されない場合の自動削除は保証しない。
残留を理由に、既存ファイルの無条件上書き・再利用・自動削除を導入しない。

## 既知の制約

### 終了処理を実行できない場合の残留

SIGKILLによる強制終了や停電などでは、token fileがファイルシステムに残る。
権限やファイルシステムの状態によって、クリーンアップ時の削除が失敗する可能性もある。

0600権限は通常のファイルアクセス権に従う別ユーザーからの読み取り・書き込みを制限する。
排他生成とsymlink拒否は、既存ファイルの利用やリンク先への書き込みを防ぐ。
これらは同一UIDのプロセスや特権ユーザーからのアクセス、親ディレクトリの権限に依存する
差し替えを包括的に防ぐ仕組みではない。残留だけで直ちに漏洩したとはいえないが、秘密情報が
ディスク上に残る期間と、バックアップ等へ複製される機会は増える。

### 次回起動への影響と現行の復旧手順

現行実装は、0600であっても既存token fileを拒否する。このため、残留ファイルがある同じ
パスでは次回起動が失敗する。これはADR-0107で定めたfail-closed動作である。

運用者は旧daemonが停止していることを確認したうえで、残留ファイルを手動で削除し、
再起動する。生存状態が不明な場合にファイルを消して再起動してはならない。
残留ファイルを安全に自動判定・回収する方式は未実装である。

### token値の残留と認証権限の区別

ファイルが残っていても、終了したdaemonが認証要求を受け付け続けるわけではない。
次回起動では新しいランダムtokenを生成し、古いファイルのtokenは再利用しない。
したがって、停止済みdaemonの認証権限が残留ファイルだけで生存するとは扱わない。

一方、daemonが実際には生存している場合、そのインスタンスのtokenは引き続き有効である。
ファイルの削除は稼働中daemonのメモリ内tokenを失効させる操作ではない。
プロセスの生存確認と、秘密情報を保存したファイルの回収は区別する必要がある。

### 運用上の蓄積

既定の固定パスでは、一つの残留ファイルが次回起動を妨げる。起動ごとに別の
`--token-file`パスを指定する運用では、複数の古いファイルが累積しうる。
配置場所と回収責任を運用手順で管理する。

## 今後の対応

次段階の共通認可・リソース単位の権限制御と合わせ、以下を設計上の検討事項とする。
ここに挙げる方式は、現行仕様として採用済みではない。

- 残留token fileを検出した場合の、安全な自動判定・回収方法を検討する。
  無条件上書きを現行規則の例外として扱わず、変更には別途設計判断を必要とする。
- daemonのPID・起動時刻・インスタンス識別子等を用いた所有確認を検討する。
  PID再利用や確認後の状態変化があるため、PID単独を所有証明としない。
- OS管理のユーザー専用ランタイムディレクトリや一時領域への配置を検討する。
  再起動時の削除方針・権限・プラットフォーム差を確認し、単に一時ディレクトリを選ぶだけで
  電源断後の削除を保証したことにしない。
- tokenファイルの内容形式や配置場所を変更する場合は、既存クライアントの読み取り方法と
  移行手順を明示する。

## 意味差分と更新方針

- 保存: 専用ファイル、0600、排他生成、symlink拒否、プロセス終了時クリーンアップ。
- 明確化: 残留ファイルの拒否・手動復旧は既定方針であり、自動回収のみが未解決である。
- 補正: 添付案の「第三者による読み取り・差し替えを防ぐ」という表現を保護範囲に限定し、
  token値の残留を停止済みdaemonの認証権限の継続とは区別した。
- 未解決: 異常終了後の自動回収、同一UID隔離、プロセス所有確認と安全な配置場所。
- 更新契機: token形式・配置先・失効方式・自動回収・複数ユーザー対応の変更時に再評価する。
