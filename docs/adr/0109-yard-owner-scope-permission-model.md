# ADR-0109: クロニクルヤードにおける所有者スコープと権限モデル

## ステータス

Accepted（2026-09-15）

提供文書は「ともゆき氏との協議により確定」と記録されており、本ADRは利用者の登録依頼に
基づいてその設計決定を保存する。共通認可の実装完了や本番運用の承認を示すものではない。

## 適用範囲と現行実装との境界

本ADRは、Chronicle Yardで今後整備する所有者スコープと共通認可の設計原則を定める。
以下のSaaS要件は将来のプロダクト設計上の前提であり、現行Chronicle Stackをホステッドサービスへ
変更する決定ではない。現行の明示起動・loopback-local運用、JSONL一次記録、Coreを介した操作、
派生インデックスという境界は維持する。

本ADRの登録によって、スコープ／grantのモデル追加、既存リソースの所有者変更、権限付与、
データ移行、CSG-RAG・AI番頭との接続を実行しない。設計の実装は別途仕様・移行計画・検証を伴う。
「テナント」の語彙変更は本ADRに基づく今後のモデルへ適用し、既存の履歴・外部規約・公開契約の
文言を一括置換したり、互換性確認なしに既存フィールドを改名したりしない。

## コンテキスト

AI番頭の実装検討の過程で、クロニクルヤード（CY）との統合要否が議論になった。当初はAI番頭の書き出しスキーマをChronicle Stack形式へ寄せるという語彙・フォーマットレベルの整合に留まっていたが、「AI番頭で整理した知識をその後のLLM会話に利用できるべきだ」という要求により、CSG-RAGを含む検索層そのものの統合が視野に入った。

さらに、CYは将来的にザイクスの複数プロダクトで用いる想定であることが明らかになり、SaaS上での運用が前提となる以上、個々のユーザーの機密保護のためにマルチテナントを前提とした設計が必要という論点が生じた。

検討の過程で「テナント」という単位が単純なフラットな一単位ではないことが判明した。基本形は「ユーザーが組織であり、その中にメンバーあるいはチームが含まれ、組織内に複数チームが存在し得る」という構造だが、AI番頭の実例（士業事務所とその配下の顧問先）を突き合わせると、これは固定的な三層（組織／チーム／メンバー）には収まらない。士業事務所自体が「メンバー1人のチーム」であり、その下に顧問先が従属するという形で捉えると、組織・チーム・テナントを別々のプリミティブとして扱う必要がないことが分かった。

あわせて、権限関係は単純な所属の有無（2値）ではなく、メンバーとチームの多重帰属を許した上でのネットワーク（グラフ）として表現すべきという結論に至った。

なお、提供文書の作成時には、UIのHost/Origin未検査やdaemon tokenの露出がP0課題として
記録されていた。その具体的な経路はCY-1で修正され、PR #391でmainへ統合済みである。
これにより共通認可や複数ルートスコープ間の隔離が実装されたわけではない。
本番運用には、本ADRに基づく認可・分離・失効等の設計と検証を別途必要とする。

## 決定

### 1. 所有者スコープは任意深度の入れ子構造とし、深度上限をスキーマレベルで設けない

スコープ（旧来「テナント」と呼んでいたもの、あるいは「組織」「チーム」に相当するもの）は、親を持つか持たないかを問わず同一の構造として表現し、入れ子の深さに理論上の上限を設けない。将来のプロダクトがどのような所有構造を必要とするかを現時点で予見しきれないことを設計上の前提とし、深度制限によってその可能性を閉じないことを優先する。

深度無制限に伴う権限解決コストの増大は認識しているが、これは実装上の緩和策（後述）で対処すべき別問題であり、本決定を制約する理由にはしない。

### 2. 「テナント」という独立したプリミティブを廃止する

「テナント」は独立した概念ではなく、「親を持たないスコープ（ルートスコープ）」として、他のスコープと同一の構造の特殊形にすぎない。今後CYの語彙から「テナント」という用語は退場させ、「スコープ」「ルートスコープ」に統一する。

### 3. メンバーとスコープの関係は多重帰属を許す

一人のメンバーが複数のスコープに同時に属することを標準として想定する。一メンバー一スコープという単純化は行わない。

### 4. 所属構造（containment）と権限付与（grant）を別のグラフとして分離する

スコープの入れ子関係、およびメンバーがどのスコープに属するかという「所属構造」と、あるメンバー（またはスコープ）が別のスコープに対してどのような操作を許されるかという「権限グラフ」は、別個のグラフとして扱う。

所属構造上の親子関係は、権限の自動継承を意味しない。親スコープが子スコープの内容にアクセスするには、所属関係とは独立に、権限グラフ上へ明示的に辺を張る必要がある。既定では、いかなる権限も存在しない（default-deny）。

### 5. 権限は二値ではなく、強度・役割を持つ辺として表現する

権限グラフ上の各辺は、単なる「あり／なし」ではなく、強度や役割の種別を持ち得るものとして設計する。将来、担当者と上位者のような役割の強弱がプロダクト側の要件として現れた場合に、所属関係を変更せずに権限グラフ側だけで表現できるようにする。

### 6. リソースの既定帰属は最狭スコープとする

クロニクルイベント等のリソースは、既定では作成者個人（最狭スコープ）に帰属し、より広いスコープへの共有は明示的な操作によってのみ行われる。

## 具体例（検証ケース）

AI番頭の士業／顧問先モデルを、本モデルへの当てはめとして記録する。

士業事務所は「メンバー1人のルートスコープ」として表現される。顧問先は、士業スコープの子スコープとして所属構造上に従属する。士業事務所が顧問先のクロニクルを閲覧するには、この所属関係だけでは足りず、顧問先側の同意に基づいて権限グラフ上に明示的な辺が張られている必要がある。これは、既存の「横断集計は士業が個別テナントの事前同意を取り付けた場合に限る」という規約とそのまま整合する。

## 除外事項・別途定める内容

- 深度無制限に伴う権限解決コストの緩和策（閉包テーブルによる到達可能性の事前計算等の実装方式）は、本ADRの決定を変更しない実装詳細として別途定める。
- 具体的なロール語彙（担当者／上位者等の名称・序列のカタログ化）は、各プロダクトの要件を集約したうえで標準化するか、プロダクトごとに委ねるかを別途判断する。

## 前提条件（ブロッキング）

提供文書が実装着手前の条件として挙げたUI／daemonの具体的なP0修正は、PR #391で
完了している。残留token fileと同一UID隔離の制約はADR-0108に記録済みである。

## 影響

**利点**：所属関係と権限を分離することで、越境アクセスのリスクを構造レベルで低減できる。深度無制限のスコープ構造により、将来登場するプロダクトごとの所有構造の違い（AI番頭の士業／顧問先、他プロダクトでの異なる単位等）を、CYのスキーマを変更せずに吸収できる。

**リスク**：権限グラフの解決実装が複雑化し、閉包テーブル等の運用コストが発生する。ロール語彙の標準化を怠ると、プロダクト間で権限の意味がずれるリスクが残る。所属構造と権限グラフが分離されている設計は、実装者が誤って「所属＝権限」という単純化を持ち込みやすい構造でもあり、実装時のレビューで継続的に確認する必要がある。

## 実装仕様化時に明確化する事項

以下は6つの設計決定を置き換えるものではなく、実装時の未解決の詳細である。

- スコープ識別子、親関係の整合性・循環の扱い、作成・移動・削除時の規則。
- 個人の最狭スコープを特定する方法と、複数所属がある場合の作成先・共有先の明示方法。
- grantの操作種別、付与・委譲できる主体、同意の証拠、失効・有効期限、競合時の判定。
- 辺の「強度・役割」と具体的な許可操作の対応。数値の大小や所属だけを暗黙の許可にしない。
- メンバーと認証済みprincipal、記録者actor、主張・生成のoriginの対応。
- 認可変更の検索・GraphRAG投影・キャッシュへの反映と、古いgrantを利用しない条件。
- スキーマ上の任意深度を維持しつつ、解決時間・探索量等の実行予算に達した場合に
  未検証のアクセスを許可しないための挙動。

## T-RDEと更新方針

- 保存: 任意深度、ルートも同一のスコープ構造、メンバーの多重帰属、containmentとgrantの分離、
  default-deny、役割・強度を持つ辺、最狭スコープへの既定帰属と明示共有。
- 更新: 提供文書のP0未解決という時点情報を、CY-1のmain統合済み状態へ更新。
- 補足: 設計採用と実装状態の区別、既存契約の移行境界、未解決の権限解決詳細。
- 未解決: 権限解決方式とロール標準化、および上記の実装仕様化事項。
- 逸脱リスク: 所属を権限と同一視すること、深度無制限を実行資源無制限と解釈すること、
  設計上の採用を本番隔離の実証として扱うこと。
- 次回更新: 共通認可の実装着手、grantの意味確定、検索投影への適用、既存データの移行、
  新たなプロダクトの所有構造・ロール要件が明らかになった時点で再評価する。

## 2026-09-15補足: 操作種別と所有者スコープの命名方針

Agent側の操作区分は`AgentCapabilityScope`から`AgentCapabilityKind`へ改称する方針とする。
関連する`capability_scope`は`capability_kind`、`allowed_scopes`は
`allowed_capability_kinds`を移行先とする。これらは操作種別の宣言であり、grantの存在や
実際の認可成功を意味しない。所有構造と操作区分を文脈だけで読み分け続ける方式は採らない。

この設計領域の新しい語彙では、修飾なしの「スコープ」を所有者構造に予約する。
既存のcontext scope、Federation trust scopeや外部規約は別契約であり、一括改名しない。
これらの境界では修飾語と定義を明示する。

改称は未実装。公開import、CLI表示、JSONフィールド、文書、テストを一緒に移行する。
`read_context`等の列挙値と`agent.read_context`等のcapability IDは維持する。
JSONの契約バージョンと旧名の移行期間・廃止条件を実装前に定め、無告知で旧契約を変更しない。
互換エイリアスを採る場合も移行専用とし、新しい正規契約に二つの呼称を恒久的に残さない。

actor／originは来歴、メンバー／principalは所属・認証主体の概念であり、同一ではない。
文字列一致から主体の同一性を推定したり、originからgrantを導出したりしない。
検証済み主体との対応方法は引き続き実装仕様化時の未決事項とする。

### 改称実装前の確認対象

改称方針はADR内の表記だけでなく、`src/chronicle/api/agent_runtime.py`の型・フィールド、
公開export、CLIの出力契約、関連文書・テストまでを対象とする。
`cloud_authority.py`の`consent_required`・`trust_scope_required`等はこのAgent改称に
含めない。Cloud側フィールドの名称・意味はCloud整合整理で別途判断する。

外部消費者について、Sayane MCP Server向け露出ポリシー・対応表を含め、
他リポジトリのコード／文書が旧型名・旧JSONキーを参照するかを実装前に確認する。
Suggested等の設計状態と実際の利用状態を区別し、MCP未実装という記録だけから
外部消費者なしと結論しない。参照先と利用状況に基づいて契約バージョン、互換措置の要否、
移行期間を決める。今回の補足は確認項目の登録であり、外部調査完了を意味しない。
