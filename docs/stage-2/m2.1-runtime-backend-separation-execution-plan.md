# M2.1 Runtime Backend Separation Execution Plan

Status: Completed
Parent milestone: `docs/stage-2/milestones.md` (`M2.1 Runtime Backend Separation`)
Parent roadmap: `docs/stage-2/roadmap.md`
Parent specification: `docs/stage-2/basic-specification.md`

## 1. Purpose

This note turns Stage 2 M2.1 into an implementation-ready sequence for the current Python codebase.

The immediate goal is not to finish all of Stage 2. The goal is to separate provider-specific runtime execution from Chronicle-side orchestration and recording without breaking the existing CLI surface.

## 2. Current code reality

As of this plan, the runtime flow is centered on these files:

- `src/chronicle/services/runtime_service.py`
- `src/chronicle/services/runtime_config_service.py`
- `src/chronicle/cli_runtime.py`
- `src/chronicle/models/runtime.py`
- `src/chronicle/services/summary_job_service.py`
- `src/chronicle/services/artifact_service.py`

Adjacent proposal / review seams already exist and should be reused later:

- `src/chronicle/services/proposal_service.py`
- `src/chronicle/services/review_service.py`
- `src/chronicle/ui_server.py`

## 3. Current responsibility map

`RuntimeService` currently mixes four responsibilities that Stage 2 wants separated:

1. Provider contract resolution
   - reads `RuntimeConfigService`
   - decides whether execution is local placeholder or configured HTTP

2. Orchestration
   - validates allowed execution mode
   - builds invocation plan and retrieval plan
   - chooses execution path

3. Provider-specific execution
   - builds HTTP request payloads
   - performs network calls
   - parses provider response payloads

4. Chronicle-side recording
   - records assistant output events
   - creates draft summary jobs
   - creates draft artifacts

M2.1 should separate 2 and 3 first. M2.2 will separate 4 more fully.

## 4. Target structure for the first migration

Create a new package:

```text
src/chronicle/runtime/
  __init__.py
  contracts.py
  orchestrator.py
  errors.py
  requests.py
  results.py
  backends/
    __init__.py
    base.py
    disabled.py
    fake.py
    http.py
    local.py
```

This first slice should stay intentionally small:

- `contracts.py`
  - shared request / response dataclasses or pydantic models
  - backend protocol
- `orchestrator.py`
  - provider-agnostic execution path
  - backend selection through injected factory
- `backends/disabled.py`
  - explicit disabled behavior
- `backends/fake.py`
  - deterministic test backend
- `backends/http.py`
  - migrated HTTP execution only
- `backends/local.py`
  - migrated local placeholder summary behavior only

`RuntimeService` remains as a compatibility facade during migration.

## 5. First-slice scope

In scope for M2.1 implementation start:

- backend protocol
- orchestrator for `summarize` and `invoke`
- disabled backend
- fake backend
- move HTTP execution code out of `RuntimeService`
- move local placeholder summarization code out of `RuntimeService`
- keep current CLI commands and JSON output stable

Explicitly out of scope for this slice:

- capability registry
- operation plan DSL redesign
- proposal surface protocol
- transport envelope
- runtime event stream redesign
- full recording split

## 6. Compatibility rules

The following user-facing contracts should not change in this slice:

- `chronicle runtime status`
- `chronicle runtime summarize`
- `chronicle runtime invoke`
- `chronicle runtime invoke-plan`
- `chronicle runtime execute-plan`
- existing `tests/test_runtime_cli.py` JSON shapes

The migration is acceptable only if:

- current CLI commands still pass without caller changes
- current JSON response fields remain available
- Stage 2 runtime remains explicit and opt-in
- no new background runtime behavior appears

## 7. Proposed implementation order

### Step 1. Add backend protocol and fake backend

Add:

- `RuntimeBackend` protocol
- `RuntimeBackendRequest`
- `RuntimeBackendResult`
- `FakeRuntimeBackend`
- `DisabledRuntimeBackend`

Tests first:

- orchestrator can run against fake backend
- disabled backend always rejects execution
- fake backend does not touch Chronicle storage

### Step 2. Introduce orchestrator

Add `RuntimeOrchestrator` with only injected dependencies:

- config state
- backend factory
- optional clock / request id helper

Responsibilities:

- validate explicit execution
- select backend from config
- normalize backend result to existing runtime result models

Do not let orchestrator:

- call `ChronicleService.record_event`
- create artifacts
- create summary jobs

### Step 3. Migrate local placeholder execution

Move local placeholder summary generation from `RuntimeService` into `LocalRuntimeBackend`.

Keep exact behavioral expectations where feasible:

- sentence truncation behavior
- review-required semantics
- no external network

### Step 4. Migrate HTTP execution

Move these behaviors into `HttpRuntimeBackend`:

- request payload creation
- credential presence checks
- URL call
- response parsing
- provider transport / response error mapping

Keep `RuntimeService` responsible for translating backend output into current CLI-facing result models until M2.2.

### Step 5. Convert `RuntimeService` into a facade

After local and HTTP backend migration:

- `RuntimeService` becomes a thin composition layer
- planning methods may temporarily remain here
- execution methods should delegate to `RuntimeOrchestrator`

## 9. Test strategy

Required tests for this slice:

- new orchestrator unit tests
- fake backend deterministic execution tests
- disabled backend negative tests
- HTTP backend transport error tests
- local backend no-network tests
- existing CLI integration tests still passing

Minimum command validation before closeout:

```bash
ruff check src/ tests/
pytest -q tests/test_runtime_orchestrator.py tests/test_runtime_backends.py tests/test_runtime_cli.py
pytest -q
```

## 10. Failure gates for the implementation

Stop or rework if any of these happen:

- backend code directly writes to `.chronicle/chronicle.jsonl`
- backend selection leaks provider-specific payloads into CLI code
- `record=false` begins mutating Chronicle state
- current runtime CLI JSON contracts drift without intentional migration documentation
- cancellation / timeout cleanup becomes harder to express than before
- fake backend cannot cover orchestrator behavior without real network

## 11. PR slicing recommendation

Recommended implementation split:

1. `docs: add M2.1 execution plan`
2. `test: add runtime orchestrator and backend contract coverage`
3. `feat: add runtime orchestrator with disabled and fake backends`
4. `refactor: migrate local and http runtime execution into backends`
5. `refactor: reduce RuntimeService to orchestration facade`

Each PR should include:

- milestone reference: `M2.1`
- in-scope / out-of-scope
- failure conditions checked
- note that recording split is deferred to `M2.2`

## 12. Exit checklist

M2.1 implementation start can be considered complete for this repo when:

- provider-specific execution no longer lives primarily in `RuntimeService`
- fake backend can drive orchestrator tests without network
- disabled backend is the fail-closed path
- current runtime CLI remains green
- no recording redesign was smuggled into the backend layer
- follow-up work for M2.2 is listed explicitly
