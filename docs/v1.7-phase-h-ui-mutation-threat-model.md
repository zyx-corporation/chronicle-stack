## Purpose

This note captures the minimum threat model Chronicle Stack must satisfy for browser reads, session
bootstrap, and any write-capable local UI review flow.

## Current posture

- `chronicle ui` is foreground and loopback-only; read-only remains the default
- `GET /` and `GET /index.html` are unauthenticated but contain no credential, Chronicle title,
  root path, or Chronicle-derived data
- sensitive GETs and the review console require a host-only browser-session cookie
- browser-triggered write routes exist only under explicit mutation/auth/authz gates and retain CLI
  recovery semantics
- local interactive state remains ephemeral UI state; Chronicle JSONL remains authoritative
- the accepted scope is a single operator, not a same-UID or shared-machine security boundary

## Primary threats

- shared-machine operator confusion causing unintended approval actions
- self-declared reviewer identity being mistaken for enforced identity
- DNS rebinding or a foreign Host reaching the loopback UI
- cross-origin browser requests reading Chronicle data or invoking a POST route
- session or mutation credentials leaking through public HTML, startup metadata, stdout, or CORS
- one credential being reused as both read-session and mutation authority
- replay of a browser bootstrap or mutation request identifier
- future write routes bypassing audit insertion requirements
- convenience drift turning preview actions into mutation without explicit auth/authz design
- derived UI state being mistaken for durable approval state
- a fragment-bearing browser-launch URL being exposed in local opener, browser, diagnostic, or
  extension plumbing before the fragment is removed

## Required browser request controls

- exactly one accepted Host for the actual loopback port on every supported GET, POST, and OPTIONS
  request
- GET Origin may be absent, but when present must match the validated local authority
- exactly one matching Origin on POST and OPTIONS
- no CORS allow headers; OPTIONS returns a rejection rather than enabling preflight
- a public, data-free locked shell and cookie authentication on all sensitive GETs
- one-time, short-TTL fragment bootstrap delivered only by `chronicle ui --open`
- immediate fragment removal before the bootstrap POST
- no bootstrap secret in startup metadata, `--json`, stdout/stderr, or served HTML
- host-only `HttpOnly; SameSite=Strict; Path=/` cookie; `Secure` is intentionally absent while the
  accepted local origin remains plain `http://`, so the `Secure`-requiring `__Host-` prefix is also
  unavailable
- separately generated cookie and mutation-header credentials
- Host, Origin, session, route/mode, and mutation-header rejection before request-body parsing or
  Chronicle persistence

The bootstrap exchange is the only POST that does not already have a session cookie: exact Origin
and the one-time secret are the inputs that issue that cookie. Every other POST requires the cookie.

## Required controls for GUI mutation

- explicit authentication boundary for local UI sessions
- explicit authorization rule for who may approve / reject / request changes
- independent mutation header token, mutation session id, and one-use mutation request id
- audit insertion guarantee for every GUI review mutation
- CLI-to-UI parity checks for available review actions
- clear rollback / failure semantics for partial review mutation failures
- unchanged primary JSONL bytes for request-boundary rejection before mutation

## Residual risks

- `--open` passes the fragment-bearing URL through Python `webbrowser` and platform/browser opener
  integration. A 60-second TTL, one-time use, and immediate `history.replaceState` reduce but do not
  remove that local exposure window.
- A same-UID process can inspect browser/process state, connect to loopback, or access Chronicle files
  according to filesystem permissions. Cookie, SameSite, Host, and Origin checks do not claim to
  prevent that.
- Plain HTTP requires omitting the cookie `Secure` attribute and prevents use of the `__Host-`
  prefix. Non-loopback exposure remains prohibited; HTTPS would require a separate transport
  decision.
- Host-only cookie scope does not include the TCP port. A browser may send the cookie to another
  local service on the same hostname; it is not a port-isolation mechanism.
- A Unix-domain socket with filesystem permissions is a follow-up defense in depth, not a complete
  answer to hostile same-UID processes.

## Non-goals

- hosted multi-user deployment design
- remote identity provider integration
- unattended approval automation
- replacing append-only CLI review as source-of-truth mutation path without further ADR work
- same-UID process isolation or shared-machine safety certification
- claiming that the current browser opener handoff is secret from all local launch integrations
