# Daemon token残留回収の安全条件

## 着手と境界

2026-09-15の本タスクで安全条件の設計に着手し、初版を作成した。
所属構造・grant実装を待つ依存関係はない。次の工程は本案のレビューとOS別方式の検証であり、
自動回収実装の開始日・完了日は未確定。継続実装や自動実行を予約したものではない。
現在の既存ファイル拒否・手動復旧を変更しない。

## 回収を許可するための条件

以下は満たすべき設計条件であり、現在のコードが保証する事項ではない。

1. 対象ディレクトリとファイルの所有UID、アクセス権、通常ファイルであること、
   リンクや差し替えの有無を検証する。確認から更新までの競合を防ぐ方式を必要とする。
2. 全起動者を直列化し、稼働中インスタンスが所有するtokenを回収しない。
   tokenと独立した安定したロック対象を候補とするが、OSごとの解放・置換・再起動時の
   挙動を実証してから方式を決定する。ロック非対応の旧daemonは別途扱う。
3. PIDだけを所有証明としない。起動識別情報・インスタンスID・ファイル識別情報を
   関連づける。PID再利用、照会権限不足、プロセス状態不明は回収許可にならない。
   ポートが応答しないことだけでも停止証明にならない。
4. 生存する旧daemon、所有不明、旧形式で証明不能なファイルは拒否する。
   旧tokenを読み直して認証を復活させない。ファイル削除は稼働中tokenの失効ではない。
5. 回収可能と判定した対象と実際の更新対象が一致することを更新時にも保証する。
   単純なstat後のunlinkでは十分としない。別プロセスの差し替えがあれば中止する。
6. 新tokenは新しい乱数から生成し、0600の排他的な一時ファイル等を用いて安全に公開する。
   bind失敗、書込失敗、公開直前・直後の強制終了、電源断での回復状態を定義する。
   旧daemonの有効tokenを失わせる順序を認めない。永続化・公開方式は検証待ち。
7. 終了時は自インスタンスが所有する対象だけを回収する。tokenのログ・argv露出を防ぐ。

同一UIDの悪意あるプロセスや特権ユーザーへの完全な隔離は保証範囲に含めない。
token本文形式を変更する場合はクライアント互換性と移行が必要。
メタデータを別ファイルにする場合も二つのファイルの不整合を扱う必要がある。

## 実装前に検証するケース

- 同時起動、PID再利用、稼働中daemonのtoken欠落・置換。
- UID・権限違反、symlink、親ディレクトリ差し替え、照会失敗。
- 各更新段階での強制終了、再起動後の残留、ディスク書込失敗、bind失敗。
- ロック非対応の旧daemon、旧token形式、未知の所有者ではfail-closed。
- 新tokenのみで認証成功し、旧tokenは新インスタンスで拒否されること。

レビューでOS別の所有証明・排他・公開方式、移行方式を確定し、ADRに採否を記録してから
実装する。テストケースを挙げたことを、検証済みと扱わない。
